## Постановка задачи

Сервис проверяет физических и юридических лиц на присутствие в санкционных списках OFAC
(SDN и Consolidated, публикуются Минфином США). Задача типовая для банковского и
финтех-комплаенса: при онбординге клиента или перед транзакцией нужно определить,
не совпадает ли клиент с фигурантом списка.

Имя не является уникальным идентификатором, поэтому точное совпадение строк недостаточно:
нужен fuzzy-поиск с оценкой уверенности, а решения выше определенного уровня риска не могут
приниматься полностью автоматически - для них требуется отдельный признак сверх совпадения
имени (страна, дата рождения, идентификатор) либо ручное подтверждение. Дополнительное
требование - неизменяемость и проверяемость истории решений (audit trail).

## Архитектура

```
OFAC (SDN.XML, CONSOLIDATED.XML)
        |
        v
load_sanctions.py  - скачивание, streaming-парсинг XML, загрузка в БД
        |
        v
PostgreSQL 17 (pg_trgm) - хранение списка, решений, журнала аудита
        |
        v
FastAPI  - HTTP-слой: скрининг, аудит, ручное ревью
```

Загрузка списка вынесена в отдельный батч-процесс, запускаемый по расписанию через Airflow
(`airflow/dags/load_sanctions_dag.py`), не является частью долгоживущего сервиса.

## Реализация

### Загрузка данных

`load_sanctions.py` скачивает оба XML-экспорта OFAC и разбирает их потоково
(`xml.etree.ElementTree.iterparse`, без построения полного DOM-дерева в памяти). Перед
записью в БД выполняется проверка на минимальное ожидаемое количество записей
(`MIN_EXPECTED_RECORDS`) - защита от загрузки результата оборвавшейся или пустой выгрузки.
Загрузка полностью перезаписывает текущий снепшот списка (`TRUNCATE` + `INSERT`), в колонку
`source_version` пишется sha256 исходного файла.

### Нормализация и скоринг

Имена приводятся к единому виду: Unicode-нормализация, транслитерация в латиницу, удаление
организационно-правовых суффиксов (LLC, АО, GmbH и аналогичных) и стоп-слов. PostgreSQL
`pg_trgm` выполняет предварительную фильтрацию кандидатов по индексу, финальная оценка
сходства считается rapidfuzz как взвешенная комбинация `WRatio` и `token_set_ratio`
(по основному имени и всем алиасам, берется максимум). К базовому name-score добавляются
бонусы за совпадение идентификатора, страны, даты рождения и типа лица.

### Классификация решения

Итоговый score сравнивается с двумя порогами (`SCREENING_REVIEW_THRESHOLD`,
`SCREENING_MATCH_THRESHOLD`). Полностью автоматическое подтверждение (`MATCH`) допускается
только при высоком однозначном score и наличии хотя бы одного независимого признака
совпадения помимо имени. При недостаточной уверенности или неоднозначности между
топ-кандидатами решение получает статус `POSSIBLE_MATCH` и требует ручного ревью.

### Аудит

Каждое решение и каждое ручное ревью записываются в отдельные hash-chained журналы:
запись содержит хеш предыдущей записи цепочки (`previous_hash`) и собственный хеш
(`event_hash`), вычисляемый от стабильной JSON-сериализации события (`sort_keys`). Изменение
или удаление любой записи задним числом делает цепочку невалидной, что проверяется отдельным
эндпоинтом (`GET /v1/audit/verify`), пересчитывающим цепочку с нуля. Голова цепочки
читается под `SELECT ... FOR UPDATE`, что сериализует запись при параллельных запросах.
Порядок при пересчете цепочки задается отдельной monotonic-колонкой (`seq bigserial`),
назначаемой Postgres при вставке внутри уже захваченного лока, а не клиентским
timestamp'ом - `requested_at` не гарантирует порядок при конкурентной записи, реальный
порядок вставки гарантирует.

### API

FastAPI-приложение предоставляет эндпоинты скрининга (`POST /v1/screen`), получения решения
по идентификатору (`GET /v1/decisions/{id}`), подачи ручного ревью (`POST /v1/reviews/{id}`),
проверки целостности аудита (`GET /v1/audit/verify`), health/readiness проверок и метрик в
формате Prometheus (`GET /metrics`). Авторизация - статический API-ключ в заголовке
`X-API-Key`.

```
cp .env.example .env
docker compose up -d --build
python load_sanctions.py
```
